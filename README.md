# Синхронизация покупателей и сделок из amoCRM

Ночной запуск — `collect_leads_customers(is_full=True)`. Решение рассчитано на 20 тыс. покупателей и 50 тыс. сделок.

## Что изменилось

- **Раньше** для каждой записи отдельно искали совпадение внутри JSON, записывали результат и часто делали `commit`. Это давало сотни тысяч обращений к базе.
- **Теперь** покупатели и сделки лежат в отдельных таблицах `amo_customer` и `amo_lead`. Общий `abstract_customer_id` связывает их между собой. Индексы помогают быстро искать по ID CRM, точному логину и названию. Данные самой записи по-прежнему хранятся в JSONB (`general` и `api_value`), а контакты, компании и настройки отправки — в `abstract_customer`.
- Синхронизация один раз читает из базы данные для поиска совпадений. CRM читается страницами, связи определяются в памяти, а записи сохраняются пачками в одной транзакции. Клиент больше не падает, если на последней полной странице нет ссылки на следующую. У сделок читаются вложенные контакты, компании и теги.

## Как работают правила

1. Покупателя без логина пропускаем. Остальных сначала ищем по ID покупателя в CRM. Если ID не нашли, ищем по логину сохранённой сделки. Логин используем, только если он ведёт к одной общей записи; иначе создаём новую.
2. Сделку ищем по её ID в CRM и по логину покупателя. Если логин ведёт к нескольким общим записям, не используем его. Если ID и логин ведут к разным записям, объединяем их в пользу записи, найденной по ID сделки. Саму сделку тоже обновляем.
3. После успешной **полной** выгрузки удаляем покупателей и сделки, которых больше нет в выгрузке или в названии которых есть «удалить» в любом регистре. Затем удаляем общие записи, у которых не осталось ни покупателей, ни сделок. Если чтение CRM прервалось, очистка не запускается.
4. Неполный запуск (`is_full=False`) не удаляет непришедшие записи и пропускает покупателей со статусом `111349` и сделки со статусом `143`. При слиянии он переносит только записи, пришедшие в этом запуске.

## Нагрузка и запуск

- **PostgreSQL.** На 20 тыс. покупателей и 50 тыс. сделок: 3 чтения (две карты связей и номер прогона), 35 пакетных записей покупателей и сделок, 3 удаления. Плюс запись групп: повторный прогон без новых групп — до 35 команд `UPDATE … FROM (VALUES …)` по 2 тыс. групп; первое заполнение — до 70 команд `INSERT` при стандартной разбивке драйвера. Итого до 76 SQL-команд для такого повторного прогона и до 111 для первого, плюс один `commit`. Это расчёт, не замер полного объёма.
- **Память.** Строки для SQL готовятся по одной пачке, без второго полного списка. Сами документы CRM остаются в памяти до конца чтения. Если одна запись занимает 6–10 КБ в Python, только документы потребуют около 420–700 МБ на 70 тыс. записей. Фактический пик зависит от ответа CRM.
- **Перед запуском на старой базе** нужно перенести покупателей и сделки из JSONB-массивов в новые таблицы: готовой миграции в проекте нет. Рабочий адрес и авторизация amoCRM в проекте не настроены.

## Проверка

На локальном PostgreSQL 18.6, Python 3.9.25 и подставной CRM (1 000 покупателей, 2 500 сделок, 3 500 групп, дополнительное поле по 1 КиБ на запись) первое заполнение заняло около **0,74 с и 13 SQL-команд**, повторное — **0,85 с и 11 команд**. С прежним способом обновления групп повторный прогон отправлял **3 509 команд**. В каждом прогоне один `commit`. Пик рабочей памяти процесса за первое заполнение и повторный прогон — около **106 МиБ** на этих синтетических данных; сеть CRM в замер не входит.

Для модульных тестов: `python -m unittest -v`. Чтобы запустить ещё и проверки PostgreSQL, задай `TEST_DATABASE_URL` с URL тестовой БД, например `postgresql+psycopg2://user:password@localhost/test_db`. Тесты создают и удаляют свои изолированные схемы; пользователю БД нужно право `CREATE` на базу. Проверяются слияние и очистка, обрыв CRM, откат при ошибке БД и число `UPDATE` на повторном прогоне.
